# PostgreSQL Persistence

## Objective

Add PostgreSQL persistence to the Secure DevSecOps Platform API and establish a secure, repeatable database configuration and migration workflow.

The database layer is designed to keep credentials outside source control, use a dedicated least-privileged application role, and manage schema changes through version-controlled migrations.

## Architecture

The application database path is:

```text
FastAPI
   ↓
SQLAlchemy
   ↓
psycopg
   ↓
PostgreSQL
```

Application configuration is loaded separately:

```text
.env
   ↓
pydantic-settings
   ↓
app/config.py
   ↓
app/database.py
```

## PostgreSQL Setup

PostgreSQL 18 was installed locally and verified with:

```powershell
psql --version
```

The PostgreSQL service and listener were also verified.

The application uses a dedicated database:

```text
secure_devsecops
```

A dedicated application role was created:

```text
secure_devsecops_app
```

The application role owns the project database but does not have PostgreSQL server-level administrative privileges such as:

- Superuser
- Create role
- Create database
- Replication
- Bypass RLS

This follows the principle of least privilege and avoids running the application using the PostgreSQL `postgres` superuser.

## Database Authentication Verification

Application-role authentication was verified directly with PostgreSQL.

The connection was checked using:

```sql
SELECT current_user, current_database();
```

Expected values:

```text
current_user:     secure_devsecops_app
current_database: secure_devsecops
```

## Secret Management

Database credentials are not stored directly in application source code.

Local database configuration is stored in:

```text
.env
```

The file contains environment-specific values for:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD
```

The `.env` file is excluded from Git through `.gitignore`.

Ignore behavior was verified with:

```powershell
git check-ignore -v .env
```

The actual database password is not stored in the repository.

## Application Configuration

`pydantic-settings` is used to load and validate database configuration.

The settings layer is defined in:

```text
app/config.py
```

The application requires:

```text
DB_HOST: str
DB_PORT: int
DB_NAME: str
DB_USER: str
DB_PASSWORD: str
```

The database password has no hard-coded fallback. Missing required configuration causes settings validation to fail rather than allowing the application to run with unintended credentials.

Configuration loading was verified without printing the database password.

## SQLAlchemy Database Layer

Database connectivity is implemented in:

```text
app/database.py
```

The module provides:

- SQLAlchemy database URL construction
- PostgreSQL engine
- Connection pooling
- SQLAlchemy session factory

The database URL is constructed using SQLAlchemy's `URL.create()` rather than manually concatenating credentials into a connection string.

The configured stack is:

```text
SQLAlchemy
   ↓
psycopg
   ↓
PostgreSQL
```

The database URL is represented with the password masked when displayed.


This verified that SQLAlchemy and psycopg could successfully authenticate to the correct PostgreSQL database using the dedicated application role.

## Session Management

SQLAlchemy `sessionmaker` is used to create application database sessions.

The session factory is defined as:

```text
SessionLocal
```

Sessions provide a controlled unit of database work and allow transactions to be committed or rolled back.

This prevents application code from manually creating unmanaged database connections throughout the API.

## Vulnerability Data Model

The initial ORM model is defined in:

```text
app/models.py
```

The `Vulnerability` model contains:

| Field | Type | Required |
|---|---|---|
| `id` | Integer | Yes, primary key |
| `cve` | String(20) | Yes |
| `severity` | String(20) | Yes |
| `affected_component` | String(255) | Yes |
| `summary` | Text | No |

The CVE field is not globally unique because the same CVE may affect multiple components.

The integer primary key is generated by PostgreSQL.

## Database Migrations

Alembic is used for version-controlled database schema management.

The migration environment includes:

```text
alembic.ini
alembic/
alembic/versions/
```

Alembic is configured to use the application's runtime database configuration instead of storing database credentials in `alembic.ini`.

Alembic also uses:

```text
Base.metadata
```

from the application's SQLAlchemy models so schema changes can be detected automatically.

## Initial Migration

The initial migration creates the:

```text
vulnerabilities
```

table.

The migration includes both:

- `upgrade()` to create the table
- `downgrade()` to remove the table

The initial migration revision is:

```text

```

Migration state was verified with:

```powershell

python -m alembic history

```

The final schema check returned:

```text

```

This confirms that the SQLAlchemy model metadata and PostgreSQL schema are synchronized.

## Troubleshooting

### PostgreSQL CLI Not Found

PostgreSQL was installed and running, but PowerShell initially could not resolve:

```text
psql
```

The PostgreSQL binary directory was added to the Windows user PATH:

```text
C:\Program Files\PostgreSQL\18\bin
```

A new PowerShell session was opened and verification succeeded with:

```powershell
psql --version
```

### Alembic Placeholder Database URL

Alembic initially failed with:

```text
Can't load plugin: sqlalchemy.dialects:driver
```

The generated `alembic.ini` still contained Alembic's placeholder database URL.

Instead of adding real credentials to `alembic.ini`, `alembic/env.py` was configured to obtain the database URL from the application's existing runtime configuration.

This allowed Alembic to authenticate without committing database credentials.

### Unsaved Configuration Changes

An import test initially failed because changes to `app/config.py` had not been saved to disk.

The actual runtime file was verified with:

```powershell
Get-Content .\app\config.py
```

This reinforced the troubleshooting practice of verifying the artifact actually being executed before changing code.

## Security Considerations

- PostgreSQL application access uses a dedicated non-superuser role.
- The application does not authenticate as the `postgres` administrative account.
- Database credentials are stored outside source control.
- `.env` is explicitly ignored by Git.
- Database configuration is validated at application startup.
- SQLAlchemy constructs the database URL without hard-coded credentials.
- Alembic obtains credentials at runtime instead of storing them in `alembic.ini`.
- Database schema changes are version controlled through migrations.
- Staged Git changes were inspected for accidentally committed credentials before commit.

## Interview Takeaway

I implemented a PostgreSQL persistence layer for a FastAPI application using SQLAlchemy and psycopg. I separated database configuration from source code using environment variables and Pydantic settings, created a dedicated least-privileged PostgreSQL application role, and used Alembic for version-controlled schema migrations.

I verified the database connection independently, validated migration state and schema drift, persisted an ORM object through a SQLAlchemy transaction, and confirmed the resulting record directly in PostgreSQL. Database credentials remain outside Git and are loaded only at runtime.
